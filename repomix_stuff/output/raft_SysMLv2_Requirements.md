# raft - System Requirements Specification for SysML v2

## 0. Document Overview

This document contains the System Requirements Specification (SRS) for the `raft` codebase, reverse-engineered into a format suitable for ingestion by the SysModeler tool to build SysML v2 models. 

The analysed repository is the HashiCorp Raft implementation (`github.com/hashicorp/raft`), a Go library that provides a distributed consensus protocol based on the Raft algorithm. The as-built architecture consists of a central `Raft` node that manages a replicated log and coordinates with peers via a `Transport` interface. It persists state using `LogStore`, `StableStore`, and `SnapshotStore` interfaces, and applies committed log entries to a user-provided Finite State Machine (`FSM`). The system operates asynchronously using background goroutines for state management (Follower, Candidate, Leader), log replication, FSM application, and snapshotting.

## 5. Behavioral Specification - State Transition Views (state def / transitions)

### 5.1 Raft Node State Machine (STM-01)

**Description:** This state machine governs the core lifecycle and role of a Raft node within the cluster. It dictates how the node reacts to RPCs, timeouts, and cluster configuration changes to achieve distributed consensus.
**Owning Part:** PRT-01 (`Raft`)
**Driving Scenarios:** SCN-02 (Node Initialization and Shutdown), SCN-08 (Append Entries RPC), SCN-09 (Request Vote RPC), SCN-11 (Timeout Now RPC), SCN-12 (Main State Machine Loop).

**States Table:**

| State | Description | entry / do / exit actions | Provenance |
| :--- | :--- | :--- | :--- |
| `Follower` | The initial state of a Raft node. It passively receives log entries and votes in elections. | `do action runFollower;` | [CODE: state.go:16-17], [CODE: raft.go:158-257] |
| `Candidate` | The state entered when a follower's heartbeat times out. It requests votes from peers to become the leader. | `do action runCandidate;` | [CODE: state.go:19-20], [CODE: raft.go:286-441] |
| `Leader` | The state entered when a candidate wins an election. It accepts client commands, replicates logs, and sends heartbeats. | `entry action setupLeaderState; do action runLeader; exit action cleanupLeaderState;` | [CODE: state.go:22-23], [CODE: raft.go:468-561] |
| `Shutdown` | The terminal state of a Raft node after it has been stopped or removed from the cluster. | None | [CODE: state.go:25-26] |

**Transitions Table:**

**SysML v2 State Definition:**

```sysml
package RaftStateModel {
    private import ScalarValues::*;

    state def RaftStateMachine {
        entry; then Follower;

        state Follower {
            do action runFollower;
        }

        state Candidate {
            do action runCandidate;
        }

        state Leader {
            entry action setupLeaderState;
            do action runLeader;
            exit action cleanupLeaderState;
        }

        state Shutdown;

        transition TR_RAFT_01 first Follower accept heartbeatTimer if hasVote do action setStateCandidate then Candidate;
        transition TR_RAFT_02 first Follower accept shutdownCh do action returnRunFollower then Shutdown;
        transition TR_RAFT_03 first Follower accept TimeoutNowRequest do action setStateCandidateTransfer then Candidate;
        
        transition TR_RAFT_04 first Candidate accept voteResponse if newerTerm do action setStateFollower then Follower;
        transition TR_RAFT_05 first Candidate accept voteResponse if quorumReached do action setStateLeader then Leader;
        transition TR_RAFT_06 first Candidate accept electionTimer do action restartElection then Candidate;
        transition TR_RAFT_07 first Candidate accept shutdownCh do action returnRunCandidate then Shutdown;
        
        transition TR_RAFT_08 first Leader accept stepDown do action setStateFollower then Follower;
        transition TR_RAFT_09 first Leader accept checkLeaderLease if lostQuorum do action setStateFollower then Follower;
        transition TR_RAFT_10 first Leader accept AppendEntriesResponse if newerTerm do action handleStaleTerm then Follower;
        transition TR_RAFT_11 first Leader accept commitCh if stepDownAndShutdownOnRemove do action shutdownRaft then Shutdown;
        transition TR_RAFT_12 first Leader accept shutdownCh do action returnRunLeader then Shutdown;
    }
}
```

### UC-01: Client Log Application
**Primary Actor:** `ClientApplication` (ACT-01)
**Stakeholders:** `RemotePeer` (ACT-02) - receives replicated logs.
**Preconditions:** The Raft node is in the `Leader` state.
**Postconditions:** The log entry is enqueued for replication and application to the FSM, or an error is returned.
**Trigger:** The client application submits a command or barrier request.

**Nominal Path:**
1. The client calls `Apply`, `ApplyLog`, or `Barrier`.
2. The system wraps the request in a `logFuture` with the appropriate log type.
3. The system enqueues the `logFuture` to the `applyCh` channel.

## 7. Non-Functional & Interface Requirements

### 7.1 Performance
* REQ-PERF-001: The system shall support pipelining `AppendEntries` requests to increase replication throughput. [CODE: net_transport.go:447-463]
* REQ-PERF-002: The system shall apply logs sequentially if the `BatchingFSM` interface is not implemented. [CODE: fsm.go:127-133]
* REQ-PERF-003: The system shall provide a fast-path for heartbeat RPCs to avoid head-of-line blocking from disk IO. [CODE: raft.go:1436-1454]
* REQ-PERF-004: The system shall provide an in-memory ring buffer (`LogCache`) to cache recent log entries and avoid disk I/O. [CODE: log_cache.go:11-21]
* REQ-PERF-005: The system shall apply logs in batches using `ApplyBatch` if the `BatchingFSM` interface is implemented. [CODE: fsm.go:155-166]

### 7.2 Security
Not applicable - The codebase implements a consensus library that delegates network security (TLS, authentication, encryption) to the host application via the `StreamLayer` interface.

### 7.3 Reliability & Error Handling
* REQ-REL-001: The system shall apply exponential backoff for failed RPCs during log replication. [CODE: replication.go:210-216]
* REQ-REL-002: The system shall apply I/O deadlines (timeouts) to network connections. [CODE: net_transport.go:488-491]
* REQ-REL-003: The system shall restore the current term and last log from stable storage on startup. [CODE: api.go:517-536]
* REQ-REL-004: The system shall avoid deleting all records on snapshot restore if the log store implements `MonotonicLogStore`. [CODE: log.go:132-142]

### 7.4 Localisation / Accessibility
Not applicable - The codebase is a backend distributed consensus library with no user interface.

### 7.5 Deployment & Operations
* REQ-OPS-001: The system shall emit a gauge metric for the oldest log age at a configured interval. [CODE: log.go:177-192]
* REQ-OPS-002: The system shall log operational events using the `hashicorp/go-hclog` library. [CODE: api.go:260-272]
* REQ-OPS-003: The system shall allow reloading specific configuration parameters (e.g., timeouts, snapshot thresholds) at runtime without restarting. [CODE: api.go:765-789]

### 7.6 Data Management & Retention
* REQ-DAT-001: The system shall compact logs by deleting entries prior to a snapshot, retaining a configurable number of trailing logs. [CODE: snapshot.go:214-249]
* REQ-DAT-002: The system shall reap old snapshots, retaining only a configurable maximum number of recent snapshots. [CODE: file_snapshot.go:365-382]

### 7.7 Interface Requirements
* REQ-INT-001: The host application shall supply an `FSM` implementation to apply committed logs and provide snapshots. [CODE: fsm.go:15-49]
* REQ-INT-002: The host application shall supply a `LogStore` implementation for durable storage of log entries. [CODE: log.go:110-130]
* REQ-INT-003: The host application shall supply a `StableStore` implementation for durable storage of key configurations. [CODE: stable.go:6-18]
* REQ-INT-004: The host application shall supply a `SnapshotStore` implementation for storing and retrieving snapshots. [CODE: snapshot.go:42-60]
* REQ-INT-005: The host application shall supply a `Transport` implementation for node-to-node communication. [CODE: transport.go:29-67]

## 8. Architecture Gaps & Open Questions

| Observation | Evidence | Impact on the SysML v2 model | Recommendation |
| :--- | :--- | :--- | :--- |
| Security Delegation | The `NetworkTransport` uses plain TCP by default and delegates TLS/Security to the `StreamLayer` interface. [CODE: tcp_transport.go:20-24] | The SysML model does not capture internal security mechanisms for RPCs. | Modellers must ensure the context model includes a secure stream layer if the system is deployed in untrusted networks. |
| Dynamic Interface Casting (`BatchingFSM`) | The system checks at runtime if the provided `FSM` implements `BatchingFSM` to enable batching. [CODE: fsm.go:89] | Dynamic interface casting is difficult to represent purely structurally in SysML v2 without defining multiple ports or optional interfaces. | Model `FSM` and `BatchingFSM` as separate item definitions or interfaces, and use a decision node in the action flow to represent the runtime check. |
| Dynamic Interface Casting (`CommitTrackingLogStore`) | The system dynamically checks if the `LogStore` implements `CommitTrackingLogStore` to enable `RestoreCommittedLogs`. [CODE: api.go:731-735] | Similar to `BatchingFSM`, this creates conditional structural dependencies. | Document the optional interface in the structural model and represent the fallback behaviour in the state machine or action flow. |
| Legacy Telemetry Flag | The `NoLegacyTelemetry` flag controls whether old-style metrics (with peer names as suffixes) are emitted. [CODE: replication.go:353-356] | Creates conditional data flows to the `MetricsSink`. | Model the telemetry emission as a single flow, noting the configuration flag as a constraint on the data item. |
